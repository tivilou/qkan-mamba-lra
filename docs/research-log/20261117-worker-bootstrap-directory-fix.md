真实故障案例来自固定Suite `key-bias-worker-20261117T075358Z-b2e43070`，并非从成功输出中选择。紧凑报告经认证下载，9803字节，SHA256为`6f85bd71e7cac7873ebb24f7c43da556a3e82508e40283bbf9caadab4c37c80f`。20项已执行代码、协议和审阅绑定与09b0382 Git内容一致。报告的最后位置是入口109行：它要求输出目录不存在；但真实监督器必须先建立`migration/diagnostics/<run-id>`来记录启动、阶段和堆栈。两者冲突导致立即拒绝。这是我新增入口未复用既有目录协议的实现缺陷，不是BF16数值门失败。

修复只把该目录检查接到既有`key_bias_recovery.prepare_worker_output`：允许诊断目录预先存在，同时保留旧checkpoint、配置、结果、异常诊断路径及链接拒绝。该依赖纳入最终代码绑定，数量从17个执行文件变为18个。训练worker、模型、优化器路径、固定准入计划、已有适配器和成功实验均未修改。原源及两项完成结果仍按原流程复核和保留。

新增测试通过真实监督器启动独立进程，执行生产入口中从请求验证到checkpoint准备之间的实际语句，避免仅在空目录下调用辅助函数。旧代码复现“预建诊断目录被拒绝”，修复后到达checkpoint准备边界；带旧checkpoint的目录仍拒绝且内容不变。整个检查在QT2标准库环境完成，未导入原生框架。5文件补丁的14条命令记录了输入、字面输出与退出码，并实际执行回滚及重新应用；8个当前核心文件哈希保持不变。

这次未生成新的`sample-trace.v2`、中间表示或梯度值：故障发生在checkpoint和模型准备之前，四项原生准入结果均尚未产生。既有真实训练轨迹和64步证据保持各自原来的范围。标准库启动成功只能证明目录衔接修复，不能替代GPU上的迁移、精确恢复或配对轨迹验证。

唯一推荐方向是更新到新干净checkout，按[原有命令](../baselines/attention-key-bias-worker-admission.md)重试尚未执行的四项准入：零更新迁移、连续2步、中断1步、新进程恢复1步。假设是目录衔接修复后能进入真实迁移，同时保持原完整状态；成功门仍为来源/完成结果保留、科学状态精确恢复、实际模型固定两行轨迹结构/完整值/坐标/重放通过。任一失败即保持准入关闭并自动回传。预算仍为4次副本更新，每子进程900秒、阶段停滞300秒；既有成功数值、稳定性和性能实验不重跑，正式队列继续关闭。
